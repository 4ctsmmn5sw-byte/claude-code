# 明日の設計：AI 逆算型目標管理への拡張計画

最終目的：目標を入力すると、AI が必要な作業を洗い出し、達成期限・必要時間・既存の予定（Google カレンダーを含む）を考慮して、今日・明日に取り組む行動を提案する。
Google カレンダーの代替ではなく、カレンダーの確定予定の**空き時間**を使って目標達成を支援する。

## 0. 現状分析（第1段階の着手時点）

| 項目 | 内容 |
| --- | --- |
| 構成 | Next.js 16（App Router）/ React 19 / TypeScript / Tailwind CSS v4。サーバー処理・API ルート・認証・DB は無し（全ページ静的生成） |
| 保存 | ブラウザの localStorage（キー `asu-no-sekkei:v1`）に `AppData` を JSON で 1 件。`lib/storage.ts` の `Repository` で抽象化、読み込み時に項目ごとに検証し壊れた項目だけ除外 |
| 状態管理 | `lib/store.ts`（`useSyncExternalStore` の外部ストア）。配置・時刻変更は必ず `checkPlacement` を通す |
| 時間割 | 0:00 からの分（整数）に正規化。固定予定は曜日の規則 1 件＋例外日（`skipDates`）で、日付ごとに複製しない |
| ドラッグ | `@dnd-kit/react` 0.5（タッチは 300ms 長押し）、伸縮は Pointer Events |
| テスト | Vitest（ロジック）＋ Playwright（iPhone 14 サイズのタッチ操作・PC・日付） |
| 公開 | Vercel プロジェクト `asu-no-sekkei`（Root Directory `asu-no-sekkei`）、本番 https://asu-no-sekkei.vercel.app |

制約：データは端末ごと（同期なし）。サーバーが無いので、API キーや OAuth の秘密情報を扱うには第2段階からサーバー側の処理（Next.js の Route Handler）が必要。

## 全体の方針

- **既存データは消さない・勝手に移動しない**：保存形式は「追加のみ」で版を上げる。形式更新の前の元データは自動で退避
- **AI は「何をするか」だけを提案**：時刻の計算・空き時間・重複判定は通常のプログラムで厳密に行う
- **AI の提案はユーザーが編集・承認したときだけ保存**：AI に保存データの削除・変更をさせない
- **Google カレンダーは読み取り専用・一方向**：アプリから Google の予定を変更・削除する機能は作らない
- **Google の予定名・説明・参加者は原則 AI に送らない**：空き時間の長さ・時刻だけを使う
- **段階ごとに PR を作成**。main へのマージと本番公開は確認後

## 第1段階：目標管理の基盤（この PR）

### 実装内容
- 主要画面を 4 つに：**目標**（`/goals`）・**計画**（`/`、明日の時間割）・**実行**（`/today`、今日の時間割）・**振り返り**（`/review`）
- 目標：目標名・説明・達成条件・達成期限（任意）・優先度・想定必要時間（任意）・カテゴリー・進捗状態（やりたいこと／取り組み中／一時停止／やめた）
- 「やりたいことリスト」と「取り組んでいる目標」をタブで区別。「この目標に取り組む」で移動
- 作業工程：必要時間・状態（未着手／進行中／完了／省略）・作業順序（▲▼で並べ替え）・前提の工程（循環する組み合わせは選べない）
- 工程から通常のタスクを作成 →「計画」の未配置タスクに並び、既存のドラッグ／タップ配置で時間割へ
- タスク ↔ 工程 ↔ 目標 の対応を保持（タスクに `goalId` / `stepId`）
- **作業時間の実績**（`WorkLog`）と**達成**（`achievedAt`）を別々に管理
  - 目標のタスクを完了すると実績を自動記録、未完了に戻すと取り消し。手入力も可
  - 工程は自動では完了にしない（トーストで「工程も完了にしますか？」と確認）
- バックアップと復元（設定画面）：ファイルへの書き出し、ファイルからの復元（件数を確認してから）、このブラウザ内の自動退避データからの復元。**置き換える前のデータは必ず自動退避**（失敗したら復元を中止）

### 保存データの変更（v2 → v3、追加のみ）
```ts
AppData {
  schemaVersion: 3,
  tasks: Task[]            // 追加：goalId?: string | null, stepId?: string | null
  fixedEvents, settings    // 変更なし
  goals: Goal[]            // 追加
  goalSteps: GoalStep[]    // 追加（目標とは goalId で結ぶ平らな配列）
  workLogs: WorkLog[]      // 追加（作業時間の実績）
}
```
- v2 のデータは読み込み時に自動変換（既存の項目は変更なし、追加分は空）。初回読み込み時に元の v2 データを `asu-no-sekkei:v1:backup:premigrate-v3` へ一度だけ退避
- 参照先が消えた工程・実績は除外、タスクは残して紐づけだけ解除
- ⚠️ 新しい版を公開した後に古い版へ戻す（ロールバックする）と、古い版は目標データを知らないため、次の保存で目標データが消えます。戻す必要がある場合は、先に「バックアップを書き出す」で保存してください

### 必要なライブラリ・費用
追加なし・費用なし。

## 第2段階：AI による目標分解（Claude API）

### 流れ
1. 「目標」で自然な文章を入力（例：「12月までに TOEIC 800 点を取りたい。今は 650 点。平日は1時間くらいなら使える」）
2. AI が不足情報（現在地・達成条件・期限・週に使える時間）を**最大 1 回まとめて質問**（選択肢付き）
3. 回答をもとに、工程・具体的な作業・優先順位・前後関係・推定必要時間・期限までの進め方を提案
4. 提案は編集できる下書きとして表示（「推定値」であることを明示）。**承認したものだけ**目標・工程として保存

### 技術
- `@anthropic-ai/sdk`（公式 TypeScript SDK）を Next.js の Route Handler（`app/api/ai/*`、サーバー側）から呼ぶ
- モデル：`claude-opus-5-5`（既定）。構造化出力（`output_config.format` の JSON スキーマ）で受け取り、**サーバー側でスキーマと数値（必要時間の範囲、依存関係の参照先・循環、工程数の上限など）を再検証**してから返す
- AI に渡すのは目標の文章と回答だけ。保存データ・Google カレンダーの内容は送らない
- API キーは Vercel の環境変数 `ANTHROPIC_API_KEY`（サーバー側のみ）。クライアント・localStorage・GitHub には置かない
- 回数制限：1 端末（匿名 ID＋IP）あたり 1 日 N 回（初期値 10 回）。永続カウンターに Upstash Redis（Vercel Marketplace、無料枠あり）を使う想定。未設定時はサーバーのメモリ上の簡易制限
- API キー未設定時は**モックの提案**で動作（開発・確認用）

### 費用の目安
- Claude Opus 5.5：入力 $4／出力 $20（100 万トークンあたり）
- 1 回の分解：入力 約 3〜5 千トークン、出力（思考を含む）約 3〜5 千トークン → **1 回 約 $0.07〜0.12（約 10〜20 円）**。質問の往復を含めても 1 目標あたり 20〜40 円程度
- 1 日 10 回の上限なら最大でも 1 日 約 $1.2
- より安くする場合は Claude Haiku 5.5（入力 $0.10／出力 $0.50）に切り替え可能（品質とのトレードオフ。切り替えはご判断ください）
- Anthropic Console での API キー発行と**支払い設定（前払いクレジット）**が必要

### ユーザーの操作が必要なこと
Anthropic Console（console.anthropic.com）でアカウント作成 → 支払い設定 → API キー発行 → Vercel の `asu-no-sekkei` プロジェクトの環境変数に `ANTHROPIC_API_KEY` を登録（Production / Preview）。Console 側で月額の利用上限（Spend limit）も設定することを推奨。

## 第3段階：Google カレンダー連携（読み取り専用）

### 技術
- 認証：Auth.js（NextAuth v5）＋ Google プロバイダ。Google ログインでユーザーを識別し、接続情報をユーザーごとに分離
- 権限（スコープ）：`calendar.calendarlist.readonly`（カレンダー一覧・選択用）と `calendar.events.readonly`（予定の読み取り）。書き込み権限は要求しない
- 更新トークン：AES-256-GCM で暗号化して DB に保存（鍵は環境変数）。DB は Vercel Marketplace の Postgres（Neon、無料枠あり）を想定
- 予定の読み込みはサーバー側で行い、アプリには時間割の表示に必要な項目（開始・終了・終日フラグ・予定名・カレンダー名）だけを返す
- アプリ側のキャッシュは**別キー**（`asu-no-sekkei:gcal-cache:v1`）に保存し、既存の保存データには混ぜない
- 同期：アプリ起動時と手動更新。最終同期時刻とエラーを表示
- 対応ケース：通常／毎週の繰り返し（`singleEvents=true` で展開）／繰り返しの例外／終日／日付をまたぐ予定（日ごとに分割）／キャンセル（除外）／複数カレンダー／タイムゾーン（Asia/Tokyo に正規化）／Google 側の変更・削除（同期ごとに置き換え）／既存の固定予定との重複（警告表示、自動削除しない）
- 表示：「G」マーク付き・別の色で、ドラッグ不可
- 接続解除：Google 側のトークンを失効させ、DB から削除

### Google Cloud の設定と制限（要確認・ユーザー操作）
- Google Cloud でプロジェクト作成 → Google Calendar API を有効化 → OAuth 同意画面（ユーザーの種類「外部」）→ OAuth クライアント ID（ウェブ）を作成し、承認済みリダイレクト URI に `https://asu-no-sekkei.vercel.app/api/auth/callback/google` を登録
- カレンダーのスコープは「機密性の高いスコープ」。**公開ステータスが「テスト」の間は、登録したテストユーザー（最大 100 人）だけ**が使え、**更新トークンは 7 日で失効**（毎週再接続が必要）
- 「本番」に公開すると、機密性の高いスコープは Google の**審査（確認）**が必要（プライバシーポリシー・ホームページ・動画などの提出、数日〜数週間）。審査前は「未確認のアプリ」警告が出て、利用者数にも上限がある
- 個人利用ならテストモードのまま（自分をテストユーザーに登録）で開始し、週 1 回の再接続を受け入れるのが現実的
- 費用：Google Calendar API・OAuth は無料（割り当て内）。DB は無料枠で開始可能
- 参考（2026年10月確認）：[Manage App Audience](https://support.google.com/cloud/answer/15549945?hl=en)、[Using OAuth 2.0 to Access Google APIs](https://developers.google.com/identity/protocols/oauth2)、[Sensitive scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification)。カレンダーのスコープの分類（機密性の高いスコープかどうか）と審査期間は、第3段階の着手時に Google Cloud コンソールで再確認する

## 第4段階：逆算スケジューリング

- 目標ごとの残り必要時間＝（想定時間または工程の合計）−（完了した工程の時間）。実績は参考表示
- 空き時間の計算：Google カレンダー＋毎週固定予定（休みの日を除く）＋既存タスクを統合。同じ Google の予定は ID で一意にして二重に数えない
- 活動可能時間（例 7:00〜23:00）と休憩時間（作業の前後 N 分）を設定で指定
- 割り当て：期限・優先度・必要時間・前後関係（前提が終わる前に置かない）を考慮した貪欲法（決定的なプログラム）。AI は作業内容の提案だけ
- 時間が足りない場合は詰め込まず「期限までに X 時間不足」と警告
- AI に送るのは「何分の空き枠がいくつあるか」程度の匿名化した情報だけ（Google の予定名・説明・参加者は送らない）
- 配置案はプレビュー表示し、**承認したものだけ**タスクとして時間割に追加

## リスクと対策

| リスク | 対策 |
| --- | --- |
| 端末ごとの保存で、端末変更・サイトデータ削除で消える | バックアップの書き出し／復元（第1段階）。第3段階以降も主データは localStorage のまま（勝手にクラウドへ移さない） |
| 保存形式の更新・ロールバックでのデータ消失 | 追加のみの形式変更、移行前の自動退避、復元前の自動退避 |
| AI の費用超過 | 必要なときだけ実行、1 日の回数制限、Console の利用上限、モックでの開発 |
| AI の誤った見積もり・提案 | 推定値と明示、サーバー側で形式・数値を検証、承認制 |
| OAuth トークンの漏えい | サーバー側のみで保持、暗号化して保存、最小の読み取り権限、接続解除で失効 |
| Google の審査・テストモード制限 | 個人利用はテストモードで開始。公開範囲を広げる場合は審査を準備 |
| カレンダーのプライバシー | 予定の詳細を AI に送らない、表示に必要な項目だけを扱う |
